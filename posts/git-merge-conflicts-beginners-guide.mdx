# Git Merge Conflicts: A Practical Beginner's Guide

Imagine you're working on a project with a teammate. You both modify the same line of code, but in different ways. When Git tries to combine your changes, it may not know which version to keep. This situation is called a **merge conflict**.

Merge conflicts are a normal part of collaborative development. They don't mean your repository is broken or that you've done something wrong. They simply mean Git needs your help deciding how certain changes should be combined.

In this guide, you'll learn what causes merge conflicts, how Git identifies them, and how to resolve them safely. We'll also create a real merge conflict in a sample repository, fix it using Git commands, and explore best practices for avoiding unnecessary conflicts.

## 1. Prerequisites and Setup

Before getting started, make sure you have the following:

- **Git installed:** You'll need Git to create branches, make commits, and resolve merge conflicts. Check your installation by running `git --version`.
- **A code editor:** Visual Studio Code is recommended because it provides a visual interface for resolving merge conflicts.
- **Basic Git knowledge:** Familiarity with commands such as `git add`, `git commit`, and `git switch` will be helpful.
- **A terminal:** You can use PowerShell, Git Bash, or the integrated terminal in VS Code.

We'll create a separate practice repository for this tutorial, so you won't need to modify any existing projects or connect to GitHub.

> [!IMPORTANT]
> Perform the exercises in a separate practice repository, not inside a project containing important uncommitted changes.

## 2. Core Concepts

A **merge conflict** occurs when Git cannot automatically combine changes from two branches. This commonly happens when both branches modify the same lines of a file differently, or when one branch deletes a file that another branch modifies.

### Understanding Git Branches

A branch is an independent line of development within a Git repository. Developers use branches to work on features, fix bugs, or experiment without immediately affecting the main project.

For example, consider a project with two branches:

- **main:** Contains the stable version of the project.
- **feature:** Contains changes being developed separately.

Both branches can evolve independently. When the feature is ready, its changes can be merged into `main`.

### How Git Merging Works

Git typically uses a **three-way merge** when combining diverged branches. It compares three versions:

1. **Common ancestor:** The most recent shared commit between the branches.
2. **Current branch (HEAD):** The version on the branch receiving the changes.
3. **Incoming branch:** The version being merged into the current branch.

Git uses these versions to determine how the changes should be combined.

If changes affect different parts of a file, Git can usually merge them automatically. However, if both branches make incompatible changes to the same content, Git may require manual intervention.

### Understanding Conflict Markers

When a content conflict occurs, Git may insert special markers into the affected file.

For example, imagine both branches modify the same greeting:

```text
&#60;&#60;&#60;&#60;&#60;&#60;&#60; HEAD
Hello from the main branch!
&#61;&#61;&#61;&#61;&#61;&#61;&#61;
Hello from the feature branch!
&#62;&#62;&#62;&#62;&#62;&#62;&#62; feature
```

These markers identify the conflicting sections:

- `&#60;&#60;&#60;&#60;&#60;&#60;&#60; HEAD` marks the beginning of the current branch's version.
- `&#61;&#61;&#61;&#61;&#61;&#61;&#61;` separates the two versions.
- `&#62;&#62;&#62;&#62;&#62;&#62;&#62; feature` marks the end of the incoming branch's version.

To resolve the conflict, you must edit the file and decide which content to keep. You can keep either version or combine both into a new version.

For example, a possible resolution is:

```text
Hello from the main branch!
Hello from the feature branch!
```

After resolving the conflict, remove all conflict markers, save the file, and stage it using `git add`.

> [!NOTE]
> Git does not automatically know which conflicting change is correct. The developer must decide how to combine the changes while preserving the intended behavior of the project.

In the next section, we'll reproduce this situation in a small practice repository and resolve it using Git commands.

## 3. Step-by-Step Implementation

Now that we understand how merge conflicts work, let's reproduce and resolve one in a practice repository.

We'll create two branches, modify the same line differently, and attempt to merge them. All commands in this example have been tested using Git and PowerShell on Windows.

### Step 1: Initialize a Practice Repository

Open PowerShell or the VS Code integrated terminal and run:

```powershell
mkdir git-conflict-practice
cd git-conflict-practice
git init -b main
```

Verify that the repository was initialized:

```powershell
git status
```

Git should report that you're on the `main` branch with no commits yet.

> [!NOTE]
> Create this repository outside any existing Git repository to keep the exercise independent.

### Step 2: Create the Initial Commit

Create a file containing a simple greeting:

```powershell
Set-Content -Path greeting.txt -Value "Hello, World!"
```

Stage and commit the file:

```bash
git add greeting.txt
git commit -m "Initial commit with greeting"
```

Both branches will start from this initial commit.

### Step 3: Create and Modify the Feature Branch

Create a new branch:

```bash
git switch -c feature
```

Change the greeting:

```powershell
Set-Content -Path greeting.txt -Value "Hello from the feature branch!"
```

Commit the change:

```bash
git add greeting.txt
git commit -m "Update greeting on feature branch"
```

The `feature` branch now contains its own version of `greeting.txt`.

### Step 4: Modify the Same Line on Main

Switch back to `main`:

```bash
git switch main
```

Modify the greeting differently:

```powershell
Set-Content -Path greeting.txt -Value "Hello from the main branch!"
```

Commit the change:

```bash
git add greeting.txt
git commit -m "Update greeting on main branch"
```

Both branches have now independently modified the same original line.

### Step 5: Trigger the Merge Conflict

While on `main`, attempt to merge `feature`:

```bash
git merge feature
```

Git reports:

```text
Auto-merging greeting.txt
CONFLICT (content): Merge conflict in greeting.txt
Automatic merge failed; fix conflicts and then commit the result.
```

This happens because Git cannot automatically determine which greeting should be kept.

Check the repository status:

```bash
git status
```

Git identifies `greeting.txt` as modified on both branches.

Inspect the file:

```powershell
Get-Content greeting.txt
```

You'll see conflict markers:

```text
&#60;&#60;&#60;&#60;&#60;&#60;&#60; HEAD
Hello from the main branch!
&#61;&#61;&#61;&#61;&#61;&#61;&#61;
Hello from the feature branch!
&#62;&#62;&#62;&#62;&#62;&#62;&#62; feature
```

### Step 6: Resolve the Conflict

Open the conflicting file in VS Code:

```powershell
code greeting.txt
```

Replace the conflicting content with:

```text
Hello from the main branch!
Hello from the feature branch!
```

We've chosen to preserve both greetings because both are valid for this example.

Save the file and verify its contents:

```powershell
Get-Content greeting.txt
git diff --check
```

The first command displays the resolved file. The second checks for whitespace errors.

> [!IMPORTANT]
> Remove all conflict markers before completing the merge. Also review the resulting content to ensure it behaves as intended.

### Step 7: Complete the Merge

Stage the resolved file:

```bash
git add greeting.txt
```

Check the status:

```bash
git status
```

Git should report that all conflicts are fixed but the merge still needs to be completed.

Create the merge commit:

```bash
git commit -m "Merge feature branch and resolve greeting conflict"
```

### Step 8: Verify the Result

Run:

```bash
git status
git log --oneline --graph --all
```

Git should report a clean working tree and display a history similar to:

```text
*   477de94 Merge feature branch and resolve greeting conflict
|\
| * ee122db Update greeting on feature branch
* | 4bb1831 Update greeting on main branch
|/
* ccbaef8 Initial commit with greeting
```

The commit hashes will differ between repositories.

Finally, check the file:

```powershell
Get-Content greeting.txt
```

Expected output:

```text
Hello from the main branch!
Hello from the feature branch!
```

Congratulations! You've successfully created, identified, resolved, and completed a Git merge conflict.

> [!TIP]
> If you start a merge but decide not to continue, `git merge --abort` can usually restore the pre-merge state. However, avoid relying on it when you have unrelated uncommitted changes, because restoration may not always be possible.

## 4. Best Practices & Common Pitfalls

Merge conflicts are a normal part of collaborative development, but following good Git practices can make them easier to manage. Here are some useful habits and common mistakes to watch out for.

### Best Practices

**1. Keep your branches updated**

When working on a feature branch, regularly incorporate changes from the main branch. This helps you identify conflicting changes earlier instead of discovering them all at once.

For example, while on your feature branch:

```bash
git fetch origin
git merge origin/main
```

This fetches the latest remote changes and merges the remote `main` branch into your current branch.

**2. Make small, focused commits**

Avoid combining unrelated changes into a single large commit. Smaller commits make it easier to understand what changed and identify the source of a conflict.

Use meaningful commit messages that describe the changes being made.

**3. Communicate when working on shared files**

If multiple developers are editing the same files, communicate about the changes beforehand. This is particularly useful when modifying configuration files or shared components.

**4. Review conflicts carefully**

Don't automatically accept the current or incoming version without understanding the changes.

Sometimes the correct resolution is to keep one version, while other situations require combining both changes.

**5. Test after resolving conflicts**

A successful merge does not guarantee that the application still works correctly.

After resolving conflicts, run the project's relevant tests and verify that the merged changes behave as expected.

### Common Pitfalls

| Common Mistake | Why It's a Problem | Better Approach |
| :--- | :--- | :--- |
| Accepting changes without reviewing them | Important functionality may be lost | Understand both versions before choosing |
| Leaving conflict markers in files | Can cause syntax errors or broken behavior | Remove all markers and review the file |
| Making large, unrelated changes | Makes conflicts harder to understand | Keep changes small and focused |
| Using `git push --force` carelessly | May overwrite commits on a shared remote branch | Avoid force-pushing shared branches |
| Skipping tests after merging | Conflicting changes may introduce bugs | Run tests and verify functionality |

### What If You Make a Mistake?

If you're in the middle of a merge and want to cancel it, you can usually run:

```bash
git merge --abort
```

This attempts to return your working tree to its pre-merge state.

However, if you have unrelated uncommitted changes, Git may not always be able to restore everything automatically.

You can also inspect the current state of your repository using:

```bash
git status
```

This command is particularly helpful when you're unsure whether Git is waiting for a conflict resolution, a commit, or another action.

> [!TIP]
> Before resolving a complicated merge conflict, review the changes carefully and make sure important work is committed or safely backed up. Understanding the conflict is more important than resolving it quickly.

## 5. Conclusion & Next Steps

Merge conflicts might seem intimidating when you first encounter them, but they're a normal part of working with Git, especially when collaborating with other developers.

In this guide, we explored why merge conflicts happen, how Git identifies conflicting changes, and how to resolve them manually.

We also created a practice repository, made different changes on two branches, triggered a real merge conflict, and successfully combined both changes into a merge commit.

The key takeaways are:

- **Understand the conflict:** Review the current and incoming changes before deciding what to keep.
- **Resolve carefully:** Remove conflict markers and ensure the final file contains the intended changes.
- **Verify your work:** Use commands such as `git status` and `git log` to inspect the repository after merging.
- **Follow good practices:** Keep commits focused, communicate with collaborators, and test your changes after resolving conflicts.
